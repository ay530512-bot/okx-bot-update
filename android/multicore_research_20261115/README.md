# 1.2.5 다중 프로세스 계산 비교 — 2026-11-15

**실제 실행 결과: 2·4·8개 계산 프로세스에서 후보 계산 시간이 줄었다. 4개는 두 시험 시나리오에서 반복 계산 약 61%, 전체 재계산 약 63% 단축했다. 단, 폴드에서 측정한 결과가 아니며 실거래 배포는 하지 않았다.**

현재 방식을 그대로 유지할 이유만 있는 결과는 아니다. 계산 분리는 추가 검증 가치가 있다. 폴드 적용 후보는 2개와 4개이며, 8개를 모두 채우는 것을 기본값으로 확정하지 않는다. 실제 폰의 발열·배터리·장시간 지연·주문 경로를 확인해야 한다.

## 시험 조건

- 기준: 현재 배포 1.2.5(host-v23), 고정 코어 7.32-Q2X. 기준 코드 자체를 작업별 프로세스에서 실행했다.
- 환경: Linux x86_64, Python 3.12.14, 보이는 논리 CPU와 허용 affinity 각 9개. 실제 폴드/Android가 아니며 호스트 자원 공유와 제한을 모두 통제한 전용 장비도 아니다.
- 기존 프로세스 안에서 계산하는 방식, 별도 계산 프로세스 1·2·4·8개를 비교했다. 프로세스 개수이며 물리 코어에 고정 배치하거나 8코어 균등 사용을 강제하지 않았다.
- 같은 289종목 입력: 보존 OP 봉 자료를 복제한 1개 신호+288개 대기 상황, 58개 신호+231개 대기 상황. 나머지 종목은 고정 OHLCV 합성 자료다. 실제 289종목 시장의 빈도를 재현한 자료가 아니다.
- 각 조합 3회, 무작위 고정 순서의 독립 실행 30회, 합계 900회 스캔. 사전 smoke 2회·60스캔은 성능 집계에서 제외했다.
- 매 실행: 최초 1회, 동일 입력 반복 20회, 한 종목 과거 봉 정정 4회, 전체 종목 봉 정정 3회, 신호 만료 1회, 다음 확정봉 누락 1회.
- 부모의 자료 직렬화·전달, 작업자의 자료 준비·검사, 결과 반환·병합·기존 우선순위 정렬을 경과 시간에 포함했다. 해시 계산과 프로세스 시작 시간은 별도다.
- 실험 전 plan.json에 가설·판정 기준·코드 해시를 기록했다. 전체 결과를 본 뒤 매개변수를 조정한 재탐색은 없다.

## 측정값

시간은 중앙값이다. 반복 p95는 총 60개 표본, 전체 재계산은 9개 표본이다. 메모리는 부모+작업 프로세스의 PSS 합계(공유 페이지를 비례 배분)이며 실제 봇 전체 메모리가 아니다. 각 실행 종료 직전 값이며 최대 메모리가 아니다. CPU 합계는 부모 CPU 시간과 작업자의 역직렬화·계산·결과 직렬화 구간을 더한 계측값이다. 작업자 송수신 봉투 처리와 시작/종료 비용 등은 빠져 있어 시스템 전체 CPU 사용량이나 전력 측정이 아니다.

## 개선점과 비용

- **4개 분산:** 대기 위주 반복 계산 6.09→2.39ms(60.8% 단축), 전체 재계산 583.1→212.6ms(63.5% 단축). 신호가 많은 상황도 각각 61.1%, 63.3% 단축했다.
- **8개 분산:** 대기 위주 전체 재계산은 143.3ms까지 줄었다. 메모리는 301.0MiB로 기존 99.7MiB보다 약 3배였다. 신호가 많은 상황은 308.6MiB였다.
- **총 CPU 작업량은 감소하지 않았다:** 전체 재계산 기준 4개는 약 23~26%, 8개는 약 31~36% 증가했다. 동시에 처리해서 일찍 끝나지만 자료 전달 등의 추가 작업이 생긴다. 배터리·발열 개선은 측정하지 않았다.
- **1개 외부 작업자만 쓰면 손해:** 대기 위주 전체 재계산은 18.1%, 신호가 많은 상황은 28.1% 느려졌다. 프로세스를 분리하는 것 자체가 속도를 보장하지 않는다.
- 부모 프로세스의 5ms 간격 진단 스레드 지연 p95는 대기 위주에서 8.06ms→4개 5.98ms, 신호가 많을 때 9.96ms→4개 9.36ms였다. 합성 스케줄링 지표로, 실제 웹소켓·화면·주문 응답 측정이 아니다. 이 수치로 끊김 개선을 주장하지 않는다.

## 결과 일치 및 아직 검증하지 않은 부분

- 900회 스캔의 각 동일 시나리오에서 전체 후보 내용과 기존 우선순위 정렬의 SHA256이 모두 일치했다. 만료·다음 확정봉 누락 결과도 일치했다.
- 작업 프로세스는 신호 후보까지만 계산한다. `stream.ready=False`로 주문 경로에 진입하지 않는다. 네트워크/API 키/실제 계정/실제 주문은 사용하지 않았다.
- 이 결과는 신호 계산 병렬화 가능성 검증이다. 실제 주문 수량·중복 방지·최종 시세·손절 주문·연결 복구의 통합 통과 판정은 아니다. 수익성 시험도 아니다.
- 프로토타입은 요청 번호가 맞는 응답만 합친다. 실전 구현에는 응답 도착 시 확정봉 버전·신호 만료·접속 세대·보유/주문 상태를 부모에서 다시 검증해야 한다. 작업 중 계정/연결 상태 변화나 작업자 장애에 대한 실전 통합 시험은 하지 않았다.
- 계정 REST 대기, 실제 289종목 시세 수신 부하, 모바일 UI, 폴드 장시간 발열·OS 자원 제한을 재현하지 않았다. 따라서 위 ms 수치를 폴드 화면의 평균 5초에 직접 곱하면 안 된다.

## CPU 표시 해석과 적용 판단

`phone_performance.py`의 표시 계산은 `100 × 프로세스 CPU 시간 증가 / 실제 시간 증가`다. **“1코어 기준”은 단위이며, 코어 하나만 사용하도록 잠갔다는 뜻이 아니다.** 105%는 해당 프로세스가 평균 약 1.05코어 분량의 CPU 시간을 사용했다는 의미다. 모든 코어를 같은 성능으로 볼 수 없어 단순히 8로 나눈 값을 실제 성능 여유로 해석하지 않는다.

분산 구현 시 기존 표시가 부모 프로세스만 집계하면 CPU가 줄어든 것처럼 보일 수 있다. 부모와 작업자의 합계 CPU·메모리도 함께 표시해야 한다.

**판정:** 사전 기준(최초/전체 재계산 중앙값 20% 이상 단축, 반복 p95 악화 10% 이내, 결과 일치)을 두 시나리오에서 2·4·8개 방식이 충족했다. 1개 외부 작업자는 불충족이다. 다음 실제 기기 시험 후보로 2·4개를 권하며, 폴드 실측 없이 8개 실전 적용은 권하지 않는다. 현재 폰의 실행 파일·매매 규칙·업데이트 채널은 변경하지 않았다.

## 재현과 파일

새로운 연구용 체크아웃에서만 실행한다. 실행 중인 폰의 okx-phone 경로에서 설치용으로 사용하지 않는다. `prepare_offline.py`는 고정 원본 ZIP과 함께 보존한 host-v23 소스를 준비하며 기존 파일 내용이 다르면 중단한다. 봇을 실행하지 않는다.

python -m pip install websocket-client==1.8.0
python -B android/multicore_research_20261115/prepare_offline.py
