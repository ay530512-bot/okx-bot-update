# OKX Ai trade 1.5.2

공개 시세 수신 부하와 연결 복구 범위를 수정했습니다. 활동·설정 → 폰 새 버전 확인 → 1.5.2 설치로 적용합니다.

- 전체 종목 ticker 감시와 진입·보유 종목의 ticker/trades/books5/mark-price를 서로 다른 연결에서 받습니다. 감시 연결 재접속 때문에 정상인 진입·보유 연결의 세대와 후보 계산을 초기화하지 않습니다.
- websocket-client의 Python UTF-8 검사를 완성된 메시지의 엄격한 CPython UTF-8 디코딩으로 대체했습니다. 잘못된 문자·분할 메시지·종료 프레임 검사 및 TLS 인증서/호스트 검증을 유지합니다. 시세를 샘플링하거나 버리지 않습니다.
- 각 연결의 세대·시세 저장·구독 간격/횟수 제한·heartbeat·재접속 상태를 분리했습니다. 진입 대상으로 승격한 종목은 진입용 연결에서 새 자료를 받아야 합니다. 감시 시세를 주문용 자료로 대신 쓰지 않습니다.
- 화면과 진단파일에 진입·보유/전체 감시의 연결 상태와 끊김 횟수를 함께 기록합니다. 구독 요청 전송과 거래소의 구독 확인을 구분합니다. 거래가 없어 trades가 오지 않는 경우도 기존 유효시간 검사를 유지합니다.
- 1.5.1의 매매규칙·봉 마감 기준·90초 신호 만료·시세 유효시간·수량·손절·추적·계정·설정·로그인·인계 동작과 CSS는 동일합니다. 설치는 기존 포지션 보호 및 실행기 인계 검사를 거칩니다.

## 검증

220개 Python 검사 및 JavaScript 화면 검사를 통과했습니다. 실제 전략·진입·체결 확인·보호주문 경로는 가짜 거래소 응답을 사용하는 회귀 검사로 확인했습니다. 실제 거래소 주문 요청은 0건입니다.

최초 188개 검사에 더해, 같은 1.5.2 실행 파일로 진입 연결 검증 32개를 추가했습니다. 두 꼬리·확정반전·눌림목 롱/숏, 추세 롱, 오전 숏의 8개 조합을 각각 첫 구독·감시 연결 단절·실행 연결 복구·최초 시작 상태에서 확인했습니다. 후보의 실행 시세가 없는 상태부터 구독 요청, 시세 수신, 실제 엔진의 주문 요청·모의 체결·손절 확인까지 이어졌고, 각 경우 동일 신호의 주문 요청은 정확히 1회였습니다. 4개 시세 중 하나라도 없거나 이전 연결 자료만 남아 있으면 주문하지 않는 것도 확인했습니다. 상세 결과는 `dynamic_entry_results.json`이며, 이 추가 검증으로 실행 파일이나 설치 버전은 바뀌지 않았습니다.

websocket-client 1.8.0에서도 전송/분리 회귀 36개를 통과했습니다. 기본 검증 환경은 Python 3.12, websocket-client 1.9.2입니다.

로컬 TLS/WebSocket 서버에서 290종목 감시와 2종목 실행 시세를 120초 동안 수신했습니다. 감시 시세 132,024건, 실행 시세 18,352건을 전송하면서 감시 연결 2회와 실행 연결 1회의 실제 소켓 EOF를 주입했습니다. 모두 재접속·재구독했고, 감시 단절 중에도 실행 시세가 유효한 관측 162건이 있었으며 마지막 상태는 시세 준비 완료였습니다. 의도한 EOF 외 추가 단절은 관측되지 않았습니다. 이 수치는 로컬 합성 시험이며 폴드 또는 OKX의 장시간 실측이 아닙니다.

별도의 동일 합성 ticker 60,000건 수신/처리 비교에서는 CPU 4.576초 → 0.512초(약 88.8% 감소), 처리량 약 8.96배였습니다. 해당 수신 경로의 비교이며 전체 앱·휴대폰 성능이 같은 비율로 개선된다는 뜻은 아닙니다.

이 작업 환경에서는 ws.okx.com의 직접 DNS/연결을 사용할 수 없어 실제 OKX WebSocket 연속 운용 검증은 수행하지 못했습니다. 원격 EOF만으로 거래소·공유기·인터넷 중 종료 주체를 확정할 수 없습니다. 장시간 폴드 운용의 무중단을 보장하거나 신호의 실제 체결을 확인한 릴리스는 아닙니다.
